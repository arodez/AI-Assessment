# Bugs & Improvement Backlog: `report_generator.py`

## Summary

This document tracks the defects and functional gaps found while auditing `report_generator.py` (see [`ANALYSIS.md`](ANALYSIS.md) for the full audit and the resolved scope decisions referenced below), plus a separate backlog of non-functional, process-level improvements needed to make the script maintainable and testable going forward.

The table below covers twelve items in scope for `report_generator_fixed.py`, ordered by priority:

- **Four confirmed defects** (dates, status matching, mutable-default state, missing-deadline handling) reproduced directly by running the script against [`data/sample_input.csv`](../data/sample_input.csv) — each one already produces wrong output on real sample data today.
- **Two functional gaps** (skipped-row accounting, unknown-status bucket) that follow directly from the resolved scope decisions in `ANALYSIS.md`.
- **Six structural/robustness gaps** — real code-level enhancements, not cosmetic process items, each with a concrete triggering scenario. Most of these need input outside the shape of the current sample file (a reordered CSV column, a missing CLI argument, the passage of real time) rather than being visible in today's sample-input report as-is.

**Severity** — impact if the issue occurs in a real report: `Critical` (wrong compliance signal reaches stakeholders), `High` (data silently lost or misclassified), `Medium` (misleading but secondary output), `Low` (cosmetic / latent).
**Priority** — how soon it should be fixed relative to the others in this backlog: `High`, `Medium`, `Low`.

## Development / process improvements

Non-functional gaps that don't change report behavior but affect how safely and collaboratively this script can be maintained going forward:

- **No dependency/environment pinning** — there's no `pyproject.toml` or `requirements.txt`, and no declared minimum Python version, even though the fixed script and its test suite will need `pytest` as a dev dependency.
- **No automated tests or CI** — there is currently no test suite and nothing runs on push/PR; add a `pytest` suite (this task) and wire it into CI (e.g., a GitHub Actions workflow) so regressions are caught automatically instead of by manual inspection.
- **No type hints or static type checking** — none of the functions declare parameter/return types; adding type hints (and optionally running `mypy`/`pyright` in CI) would have caught the `SKIPPED += 1` scoping bug (#7) as a static error rather than silent dead code.
- **No linting or formatting configuration** — nothing enforces style or catches common footguns like mutable default arguments (a linter rule for exactly this exists in most Python linters) or bare `except:` clauses. Adding `ruff` (lint + format) with pre-commit hooks would catch the mutable-default-argument bug (#3) and the bare-except pattern (#10) automatically on future changes.
- **No docstrings or module-level documentation** — none of the functions document their expected input shape, return type, or failure behavior; a future maintainer has to read the implementation to know that CSV columns are positional, not name-based (see #5).
